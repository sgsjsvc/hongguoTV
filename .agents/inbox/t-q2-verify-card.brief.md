## 二、要核查的事项

### 2.1 卡片空白是否真的消除（重点）

**不能只看代码，要实测。**

- 用 ADB 实测分类页与排行榜，**dump 出卡片坐标**
- 计算：`卡片高度 − 最下子节点底部` = 剩余空白
- **对比修复前基线**：

| 项 | 修复前（协调者实测） |
| --- | --- |
| 卡片高 | 572px |
| 图片底 | 467px |
| 标题底 | 551px |
| 集数底 | 591px |
| **底部空白** | **92px（16.1%）** |

**要求**：给出修复后的实际数值，确认空白显著减少或归零。

### 2.2 同行卡片是否等高（易忽略）

若 Q1 改用 `WRAP_CONTENT`，可能出现**同行卡片高度不一**。

- 检查同一行内所有卡片的 `y1` 与 `y2`
- 若高度不一致，**明确指出**（视觉上会参差不齐）

### 2.3 「加载更多」按钮是否真的移除

- 确认页面中**不存在**「加载更多」按钮
- 用 dump 搜索该文本

### 2.4 自动分页是否生效

- 滚动到底部，确认**自动加载**下一页
- **验证方式**：dump 中的卡片数量增加，或页码变化

> ⚠️ **静态截图不能证明「自动加载」** —— 必须验证**数据是否真的增加**（如卡片总数变化）。

### 2.5 🔴 最关键：是否真的「不频繁查询」

用户明确要求：

> 自动分页查询一定要约束好，只有当前数据展示我才进行避免频繁查询

**核查方式**：

1. **快速连续滚动到底部多次**（模拟用户急促操作）
2. 观察是否产生**重复请求**

**可用的验证手段**：

- 若 Q1 提供了请求计数日志，检查调用次数
- 或用 `adb logcat` 观察网络请求
- 或观察后端日志（若可访问）

**必须回答**：

- 连续快速滚动是否触发多次重复请求？
- 请求进行中是否会被再次触发？
- 到末页后是否停止请求？

### 2.6 边界情况

| 场景 | 期望 |
| --- | --- |
| 已到末页 | 不再请求 |
| 切换榜单 | 能重新触发 |
| 切换分类筛选 | 能重新触发 |
| 加载失败 | 不无限重试 |
| 加载中 | 不阻塞焦点，用户可继续浏览 |

### 2.7 是否有越界改动

Q1 授权文件：

- `ui/CatalogScreenView.kt`
- `SeriesAdapter.kt`
- `MainActivity.kt`（仅分页逻辑）
- `res/values*/dimens.xml`

**检查是否有其他文件被改动**（尤其 `shared/content-core/hongguo.js`、`custom-server/`）。

### 2.8 是否遗留调试日志

Q1 的 brief 建议用临时日志验证分页次数。

**检查**：是否有 `Log.d` 等调试日志残留（R13 曾专门清理过）。

## 四、环境准备

```powershell
$env:ANDROID_ADB_SERVER_PORT = "15037"
$adb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
& $adb start-server
& $adb connect 127.0.0.1:16448
& $adb -s 127.0.0.1:16448 shell wm size 1280x720
& $adb -s 127.0.0.1:16448 install -r <apk路径>
```

**D3 是 1080p @280dpi**，逻辑宽 1280/1.75 = **731dp** → 命中 `sw600dp` 档。

> 注意：D3 与 Q1 用的 D1（720p @240dpi）**分辨率不同**。
> 若发现布局差异，**如实说明**（可能是档位/密度差异，非缺陷）。
