## 一、问题（DSH 实测）

当前发布门禁（`release:check` = `npm test` + `typecheck` + `smoke`）**没有任何延迟指标**：

| 门禁项 | 是否覆盖延迟 |
| --- | --- |
| `npm test` | ❌ 功能正确性，无延迟断言 |
| `typecheck` | ❌ |
| `smoke`（3 样本清晰度+取流） | ❌ 只断言 HTTP 206/字节数，**不看耗时** |

**后果**：本轮实测发现的**取流首块间歇性 ~12 秒**可以**完全通过现有门禁**，
直到用户感知才被发现。**这就是为什么它一直没被拦住。**

## 二、必须做

### 2.1 建立可复现的延迟测量（复用 DSH 已有脚本，不要重写）

DSH 本轮已写入三个只读测量脚本（**作为起点，可重构但不得丢失测量口径**）：

| 脚本 | 作用 |
| --- | --- |
| `outputs/testing/dsh-optimization-baseline.mjs` | 全链路冷/热对比（recommend/detail/qualities/stream） |
| `outputs/testing/dsh-stream-cold-probe.mjs` | 逐剧 stream 首块冷/热 |
| `outputs/testing/dsh-stream-cold-diagnosis.mjs` | 同一剧前 3 集，判断是否按剧稳定 |

**要求**：
1. 把测量脚本**移入 `scripts/perf/`**（`outputs/` 被 gitignore，无法入库追溯）
2. 输出 **JSON + 可读摘要**，含：`p50/p95/max`、样本数、**慢样本占比**、环境信息
3. 必须**自行管理服务**（启动临时服务或明确要求既有服务），**不得依赖用户手工起服务**
4. **不得触碰用户正在运行的服务**（当前 `127.0.0.1:8788` 为用户在用，PID 35052）

### 2.2 门禁阈值（建议，DSH 会复核）

基于本轮实测（优化前）设定**回归门禁**，而非绝对性能承诺：

| 指标 | 优化前实测 | 建议门禁 |
| --- | --- | --- |
| stream 首块 **max** | 12450 ms | **≤ 1500 ms**（`t-opt-stream-latency` 目标） |
| stream 首块 **慢样本占比** | 3/5 | **= 0** |
| 详情未预取 | 3334 ms | ≤ 3500 ms（不退化） |
| 新会话推荐首屏 | 1279–2545 ms | ≤ 300 ms（`t-opt-recommend-warmup` 目标） |
| 热取流 / 热详情 | 24–27 / 1 ms | 不退化（±50%） |

⚠️ **阈值须实测校准**：先跑基线，再设定；**不要把不稳定的上游波动写死成硬门禁**
（上游 CDN 抖动是客观存在的 —— 用 **P95 + 慢样本占比** 比单次 max 更稳）。
**请给出你如何区分"我们的缺陷"与"上游抖动"的方法**。

### 2.3 纳入 `release:check`

- 新增脚本（如 `npm run perf:gate`），并**接入 `release:check` 或独立发布门禁**
- **失败必须非零退出**，并输出具体超标项
- 允许通过环境变量跳过（如 `HG_SKIP_PERF_GATE=1`），但**默认开启**
- **不得**因"环境没有网络"而静默通过 —— 无法测量时应**明确失败或明确跳过并告警**

### 2.4 门禁自身要有测试

- 对测量脚本本身写测试（如：给定合成响应，断言百分位/慢样本占比计算正确）
- **不得**用"跑一次通过"代替测试
