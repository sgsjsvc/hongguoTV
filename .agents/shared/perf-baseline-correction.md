**修正方**: dsh
**日期**: 2026-10-16
**性质**: **修正我先前的错误诊断**

---

## 一、我先前说错了什么

在 `perf-baseline.md` 中我写：

> **问题 1：详情接口无缓存**
> `server/provider.mjs:90` 的 `detail()` 每次都请求上游

**这个判断不完整。** 实测发现：

**`detail()` 自身确实没有缓存，但它调用的 `routerData()` 有缓存。**

```javascript
// shared/content-core/hongguo.js
async function routerData(url) {
    const cached = pageCache.get(url);
    if (cached && Date.now() - cached.time < 180000) return cached.value;   // ← 180 秒缓存
    const value = extractAssignedJson(await getText(url));
    pageCache.set(url, { time: Date.now(), value });
    return value;
}
```

## 三、真正的瓶颈

### 不是「缺缓存」，而是「没有预取」

| 情况 | 详情耗时 | 原因 |
| --- | --- | --- |
| 180 秒内访问过 | 1 ms | pageCache 命中 |
| **首次访问** | **1453 ms** | 需请求上游 |
| **超过 180 秒** | **1453 ms** | 缓存过期 |

**用户的实际体验**：

- 浏览推荐流时，**下一部剧的详情尚未请求** → 切过去要等 1.5 秒
- 即使刚才看过，**超过 3 分钟**后缓存过期，又要等

### 为什么单纯「加缓存」解决不了

加更长的 TTL 只对「重复访问」有效。**首次切到某部剧，无论如何都要等一次上游请求。**

**唯一解法：在用户切换之前就预取。**

## 六、我的失误

**我基于代码审查下结论，但没做「重启服务 + 首次请求」的对照测试。**

先前测量时服务已运行一段时间，`pageCache` 已有数据，所以看到「1ms」时我误以为是别的机制，
而在 `perf-baseline.md` 中又根据代码（`detail()` 无缓存）断言「无缓存」。

**两者都没错，但我没把它们联系起来。**

### 教训

**判断「有无缓存」必须清空缓存后测首次请求。**
只看代码会漏掉调用链下层的缓存；只看运行时数据会误判缓存来源。

**正确做法**：重启服务 → 测首次（冷）→ 测重复（热）→ 对比。
