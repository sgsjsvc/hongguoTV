# 算法效率测量结论：算法不是瓶颈

**测量方**: dsh
**日期**: 2026-10-16
**方法**: 微基准测试（`scripts/perf/bench-recommend.mjs`）

---

## 一、为什么要测这个

用户需求包含「**算法优化**」。在派发任务前必须确认：
**算法到底是不是瓶颈？** 否则会派发无效任务。

---

## 二、测量结果

### 推荐算法 `append()` 单次耗时

| 候选池大小 | 耗时 |
| --- | --- |
| 24 条 | **0.19 ms** |
| 128 条 | **0.62 ms** |
| 512 条（代码上限） | **2.46 ms** |

**测试方法**：每次新建 session 后调用 `append(rows, 24)`，100 次取平均。

### 对比网络耗时

| 环节 | 耗时 |
| --- | --- |
| 推荐首屏（含网络拉池） | **2514 ms** |
| 推荐翻页（池内取，纯算法） | **2 ms** |

---

## 三、结论

### ✅ 算法不是瓶颈

**判据**：

- `append()` 最坏情况（512 条池）仅 **2.46 ms**
- 推荐翻页实测 **2 ms**（纯算法路径）
- 而网络拉池需要 **2514 ms**

**网络耗时是算法的 1000 倍。**

### 算法实现评价

审查 `shared/recommendation-core.cjs` 的 `append()`：

| 特性 | 评价 |
| --- | --- |
| 多层 `filter` + `sort` | ✅ 池上限 512，O(n log n) 可接受 |
| 类型配额分配（`desired`/`counts`） | ✅ 逻辑清晰 |
| 20% 探索位 | ✅ 设计合理 |
| 字符串哈希打分 | ✅ 实测开销可忽略 |
| 池上限 512 | ✅ 已防止无界增长 |

**算法设计良好，无需优化。**

## 六、经验记录

**在派发「性能优化」任务前，必须先测量确认瓶颈位置。**

本次如果直接派发「算法优化」，会浪费一个 agent 的时间，
而真正的瓶颈（详情接口无缓存）反而可能被忽略。

**判据**：只有当某环节耗时**占端到端延迟的显著比例**（如 > 20%）时才值得优化。
本案例中算法占 2/2514 ≈ **0.08%**。
