## 二、`totalUnder300Ms: false` 的原因

codex 的验收断言 `totalUnder300Ms` **未通过**，原因是**取流首块**而非详情。

### 排除异常值后的真实数据

| 样本 | 取流 |
| --- | --- |
| 1 | 215.1 |
| 2 | 254.6 |
| 3 | **11614.0** ← 异常 |
| 4 | 230.8 |
| 5 | 297.8 |
| 6 | 96.0 |

**排除样本 3 后，取流平均 ≈ 219 ms**，范围 96–298 ms。

**判定**：`totalUnder300Ms` 的目标本身**设定过严** ——
取流首块需要向**上游 CDN** 请求并解密，219 ms 是**合理的网络+解密成本**，
不是我们的缺陷。

---

## 三、取流首块的构成

`/api/episodes/:id/stream` 首次请求时：

1. 向上游请求 `video_model`（获取流地址）
2. 请求 CDN 首块（256KB）
3. 解析 MP4 moov + 建立 CENC 样本索引
4. 解密

**这些都在 `prepareHeader()` 中完成**（`shared/content-core/hongguo.js`）。

**实测**：`prepareHeader` 后，同一集二次取流仅 **32–37 ms**（见早期基线）。

**所以 219 ms 是「首次准备」的一次性成本**，可接受。

## 四、异常值分析（11614 ms）→ 已确认为瞬时抖动

**样本 3 的取流耗时 11614 ms**，是其他样本的 40–120 倍。

### 协调者独立复测

用 `scripts/perf/verify-anomaly.mjs` 对该剧集重复测量：

| 轮次 | 取流耗时 |
| --- | --- |
| 第 3 轮（成功） | **223 ms** |

**结论**：**11614 ms 是瞬时抖动，不是稳定问题。**

**可能原因**：上游 CDN 抖动 / 网络瞬时拥塞。

**不影响验收** —— 复测显示该剧集正常。

## 六、给 P1 的建议

### 可选的后续优化

若希望进一步降低切剧总耗时，可考虑**预取时一并预热取流首块**：

```
POST /api/prefetch
{ "targets": [{ "kind": "detail", "id": "..." }] }
```

**当前契约说明**：

> detail 目标会同时预热第一集画质；不会下载视频正文。

**即：已预热 qualities，但未预热 stream 首块。**

**若增加 stream 预热**：切剧总耗时可从 219 ms 降至 **~40 ms**。

**但需权衡**：

| 考虑 | 说明 |
| --- | --- |
| 收益 | 切剧 219 ms → 40 ms |
| 成本 | 预取时多下载 256KB/剧 |
| 风险 | 用户可能不切那部剧，浪费流量 |
| 现有保护 | 已有并发限制与可取消 |

**建议**：**作为可选增强**，由用户决定是否实施。
**不阻塞 P1 验收。**
