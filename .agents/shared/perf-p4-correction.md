## 三、为什么 P4 的假设不成立

### 问题 B（`load()` 无条件清空）

**原假设**：每次 bind 都 `setImageDrawable(null)` → 滚动闪烁 → 性能问题

**实测**：`Slow bitmap uploads = 0`

**原因**：`setImageDrawable(null)` 只是**清除引用**，不涉及位图上传。
真正的位图上传发生在 `setImageBitmap()`，而缓存命中时是**内存位图**，无需上传。

**所以 B 的影响是「视觉闪烁」而非「性能」。**

### 问题 C（`GradientDrawable` 重建）

**原假设**：每次 bind 创建新对象 → 对象分配压力 → 性能问题

**实测**：`Slow issue draw commands = 0`

**原因**：`GradientDrawable` 是轻量对象，创建开销远低于 16ms 帧预算。
且**只有榜单页**会走该分支（`if (isRank || series.badge.contains("榜"))`），
分类页不触发。

**所以 C 的影响可忽略。**

### 那 Janky 5.79% 从哪来

**所有「Slow xxx」计数器均为 0**，说明 Janky 来自
**帧时间超过 16ms 的「正常但偏慢」的帧**，而非某个明确的慢操作。

**可能原因**：

1. 滚动本身的布局/测量计算量
2. 60fps 目标下余量不足（p50 已 5–8ms）
3. **测量噪声**（波动 11 个百分点说明不稳定）

**注意**：Janky 定义是「帧时间 > 16ms」，在 60Hz 设备上 17ms 就算 Janky。
**5.79% 意味着约 1/17 的帧略超 16ms** —— 这在移动设备上属**正常范围**。

## 五、测量方法的教训

### 问题 1：单次采样不可靠

第一次测分类页得 **11.98%**，诊断时得 **0.41%**，5 次采样平均 **5.79%**。

**波动 11 个百分点** —— 单次采样**不能作为结论依据**。

**教训**：Janky 类指标必须**多次采样**，报告平均值与波动范围。

### 问题 2：设备离线时不应下结论

P4 brief 基于**代码审查**，我推断「大量对象分配」「明显闪烁」，
但**没有实测依据**。

**教训**：性能问题**必须实测确认**，代码审查只能提出**假设**。

**对比**：P1（详情未预取 1453ms）、P5（轮询 1.2GB/天）都有实测证据，
所以是**已确认的问题**。P4 的 B/C 只有代码审查，属于**未确认的假设**。

### 问题 3：应区分「性能」与「正确性」

`onViewRecycled` 缺失导致的**图片错位**是**正确性缺陷**，
即使 Janky 为 0 也必须修。

**但我把它归入了「性能任务」，这是分类错误。**

## 六、对 P4 执行方的建议

**若 P4 已被认领**：

1. **问题 A 必须修**（正确性）
2. 问题 B 建议修（视觉体验），但**不要声称性能收益**
3. 问题 C 可选（无实测依据）
4. 问题 D 需先验证（测量快速滚动时的请求数）

**报告要求**：

- **不要**声称「优化了滚动性能」—— 实测基线已是流畅的
- **应**声称「修复了图片错位的正确性缺陷」
- 若做了 C/D，说明**为何做**（如代码整洁性）而非性能

**若 P4 尚未认领**：建议**调整 brief**，把重点从「性能」改为「正确性 + 体验」。
