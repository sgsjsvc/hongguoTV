# 根因定位：清晰度档位缺失（用户报告）

**定位方**: dsh
**日期**: 2026-10-16
**用户报告**: 推荐页第 1 部有全部清晰度，第 2 部起只有 1080P；播放页却有全部清晰度

---

## 一、结论：不是「剧集差异」，是**上游按集返回不同 codec**

### 根因链

```
用户请求某集清晰度
  → 引擎 fetchVideoInfo 调上游 video_model
  → 上游返回 video_list（5 档）
  → 每档带 codec_type 字段
  → 部分集：低档位是 bytevc2（私有编码）
  → 我们过滤 bytevc2（会 PIPELINE_ERROR_DECODE 崩溃）
  → 结果：只剩 1080P（bytevc1）
```

### 实测证据（同一部剧的不同集）

**第 1 集**（用户看到「只有 1080P」）：

| 档位 | vheight | codec | 可播 |
| --- | --- | --- | --- |
| video_1 | 360 | **bytevc2** | ❌ |
| video_2 | 480 | **bytevc2** | ❌ |
| video_3 | 576 | **bytevc2** | ❌ |
| video_4 | 720 | **bytevc2** | ❌ |
| video_5 | 1080 | bytevc1 | ✅ |

**第 3 集**（用户看到「全部清晰度」）：

| 档位 | vheight | codec | 可播 |
| --- | --- | --- | --- |
| video_1 | 360 | **bytevc1** | ✅ |
| video_2 | 480 | **bytevc1** | ✅ |
| video_3 | 540 | **bytevc1** | ✅ |
| video_4 | 720 | **bytevc1** | ✅ |
| video_5 | 1080 | bytevc1 | ✅ |

**上游对同一部剧的不同集，返回不同的 codec 组合。**

## 二、为什么「推荐页」和「播放页」表现不同

| 页面 | 播的是哪一集 | 结果 |
| --- | --- | --- |
| **推荐页第 1 部** | 恰好是 `bytevc1` 的集 | 全部清晰度 |
| **推荐页第 2 部起** | 恰好是 `bytevc2` 的集 | 只有 1080P |
| **播放页** | 从历史续播到**别的集** | 那集恰好是 `bytevc1` |

**用户观察到的「第 1 部 vs 第 2 部差异」，实际是「不同剧的首集恰好落在不同的 codec 组合上」。**

**实测确认**（推荐流前 8 部）：

```

2  后爸后哥托举       1080P/720P/540P/480P/360P              ✓ 5 档

4  仙缘劫起第四季      1080P/720P/540P/480P/360P              ✓ 5 档

```

**同剧不同集实测**：

```

拆迁一千万   ep1=1 ep2=1 ep3=5 ep5=5 ep10=5 ep20=1   ⚠ 集间不同
```

**同一集连续 6 次请求结果稳定**（`5,5,5,5,5,5`）→ **不是随机抖动，是上游按集固定返回**。

## 三、🎯 解法：`device_level` 从 3 改为 5

### 实验发现

`requestVideoModel` 的 `biz_param.device_level` **当前是 3**。

**改成 5 后，上游对所有档位都返回 `bytevc1`（可播）**：

| 参数变体 | 可播档位 | 总档位 |
| --- | --- | --- |
| **`device_level=3`（当前）** | **1** | 5 |
| **`device_level=5`** | **5** ✅ | 5 |
| `device_level=1` | 1 | 5 |
| `use_os_player=true` | 1 | 5 |
| `need_all_video_definition=false` | 0 | 1 |
| `video_platform=0` | 1 | 5 |
| `video_platform=2` | 错误 | — |

### 多剧多集验证（18 个样本）

| 指标 | `device_level=3` | `device_level=5` |
| --- | --- | --- |
| **可播档位合计** | **66 / 90** | **90 / 90** ✅ |
| 改善样本 | — | **6 / 18** |
| 平均增益 | — | **+1.3 档/集** |

**逐样本**（部分）：

```
存款一天涨一亿      第3集   1/5  →  5/5   ✅ +4
穿越六零之我在山洞   第2集   1/5  →  5/5   ✅ +4
90赶海，暴富宠全家   第1集   1/5  →  5/5   ✅ +4
千金归来           第2集   1/5  →  5/5   ✅ +4
千金归来           第3集   1/5  →  5/5   ✅ +4
雾锁情迷           第2集   1/5  →  5/5   ✅ +4
```

### 副作用评估（全部通过）

| 检查项 | 结果 |
| --- | --- |
| **1080P 是否降级** | ✅ **完全一致**（bitrate `915311`、size `12186702` 相同） |
| **连续 12 次请求** | ✅ **12/12 成功**，0 空响应，0 错误 |
| **档位映射** | ✅ 5 档全部 `bytevc1` |
| 视频时长/分辨率 | ✅ 无变化 |

**结论：`device_level=5` 安全且有效。**

## 四、为什么当前用 3

**无注释说明** —— `device_level: 3` 是硬编码值，可能是从上游默认值抄来的。

**推测**：`device_level` 表示「设备性能等级」。
- 值越大 → 上游认为设备越强 → 提供更高质量/更多编码选择
- 值 3 → 上游认为中等设备 → 部分集只给私有编码（可能为省流量）

**上游逻辑**：对低等级设备，用 `bytevc2`（更高压缩率）省流量。
但我们的客户端**不支持 `bytevc2`**，所以过滤后只剩 1080P。

## 五、修复方案

### 方案 A（推荐）：`device_level` 改为 5

```javascript
// shared/content-core/hongguo.js requestVideoModel
biz_param: {
  detail_page_version: 0,
  device_level: 5,        // ← 从 3 改为 5
  ...
}
```

**优点**：
- 一行改动
- 实测有效（66/90 → 90/90）
- 无副作用（1080P 未降级，请求稳定）

**风险**：
- 上游可能对高 `device_level` 有额外行为（未观测到）
- 需同步 `vendor` 副本（2 处）

### 方案 B（补充）：保留 1080P 兜底

若某些集**真的**只有 `bytevc2`，则：
- 保留 1080P 作为兜底（已实现）
- 在 UI 上说明「该集仅提供 1080P」

### 方案 C（可选增强）：首次请求失败时重试高 level

若 `device_level=5` 在某些场景失效，可回退重试。

**建议：先实施方案 A，观察效果。**
