## 三、关键结论

### 1. TV 渲染整体流畅

| 场景 | Janky% | 判定 |
| --- | --- | --- |
| 推荐流 | 0.15–0.31% | ✅ 优秀 |
| 分类页 | 平均 5.79% | ✅ 可接受 |

**Janky 定义是「帧时间 > 16ms」**，在 60Hz 下 17ms 即算 Janky。
5.79% 意味着约 1/17 帧略超 16ms —— **移动设备正常范围**。

### 2. 所有「Slow xxx」计数器均为 0

| 计数器 | 值（5 次试验） |
| --- | --- |
| Slow bitmap uploads | **全部 0** |
| Slow issue draw commands | **全部 0** |
| Slow UI thread | **全部 0** |
| Missed Vsync | **全部 0** |

**说明**：Janky 不是来自某个明确的慢操作，而是**帧时间略超预算的正常波动**。

### 3. 采样波动大，单次不可靠

同一场景测出 **0% / 4.94% / 6.09% / 6.67% / 11.27%**。

**波动 11 个百分点** → **必须多次采样**，报告平均值与范围。

## 四、对任务的影响

### P4 的问题 B/C 被推翻

| 问题 | 原假设 | 实测 |
| --- | --- | --- |
| B `load()` 无条件清空 | 滚动闪烁 + 性能 | ❌ **SlowBitmap = 0**，无性能影响 |
| C `GradientDrawable` 重建 | 对象分配压力 | ❌ **SlowDraw = 0**，无性能影响 |

**原因**：

- B：`setImageDrawable(null)` 只清除引用，**不涉及位图上传**
- C：`GradientDrawable` 是轻量对象，且**只有榜单页触发**（分类页不走该分支）

**详见 `.agents/shared/perf-p4-correction.md`。**

### P3 的定位也需要调整

P3 的收益是**消除 UI 重建的开销与闪烁**，而非修复明显卡顿。

## 六、经验记录

### 教训 1：设备离线时不应下性能结论

P4 brief 基于**代码审查**推断「大量对象分配」「明显闪烁」，
但**无实测依据**。

**正确做法**：代码审查只能提出**假设**，性能结论**必须实测**。

### 教训 2：区分「性能」与「正确性」

`onViewRecycled` 缺失导致的**图片错位**是**正确性缺陷**，
即使 Janky 为 0 也必须修。

**但我把它归入了「性能任务」—— 这是分类错误。**

### 教训 3：Janky 指标必须多次采样

单次结果波动可达 11 个百分点。

**报告规范**：给出平均值 + 范围 + 采样次数。

### 教训 4：看「Slow xxx」计数器而非只看 Janky%

Janky% 高但 Slow 计数器全 0 → **没有明确的优化目标**。

**只有 Slow 计数器非零，才说明存在可定位的瓶颈。**
