# 播放流畅度测量结论：吞吐充足，瓶颈在 HEVC 解码

**测量方**: dsh
**日期**: 2026-10-16
**方法**: 代理吞吐基准 + 编码格式审查

---

## 一、吞吐量实测（排除网络因素）

### 代理吞吐

| 块大小 | 耗时 | 吞吐 |
| --- | --- | --- |
| 512 KB × 5 | 29–47 ms | **108.7 Mbps** |
| 2 MB × 3 | 80–103 ms | **189.2 Mbps** |
| 3 并发 512 KB | 121 ms | 104.0 Mbps |

### 首块延迟

| 指标 | 值 |
| --- | --- |
| TTFB | 221–248 ms |
| 单块 TTFB | 28–43 ms |

### 判定

| 项 | 值 |
| --- | --- |
| 1080P 典型码率 | ~3 Mbps |
| **实测吞吐** | **108–189 Mbps** |
| **余量** | **36–63 倍** |

**✅ 吞吐完全不是问题。** 代理层性能优秀。

## 二、真正的瓶颈：HEVC 解码

### 所有清晰度均为 HEVC

实测某剧集的清晰度列表：

| 清晰度 | 编码 |
| --- | --- |
| 1080P | **HEVC** |
| 720P | **HEVC** |
| 540P | **HEVC** |
| 480P | **HEVC** |
| 360P | **HEVC** |

**上游只提供 HEVC（`bytevc1`）编码。**

### 为什么这会导致卡顿

| 场景 | 表现 |
| --- | --- |
| 有硬件解码（现代 GPU/电视芯片） | ✅ 流畅 |
| **无硬件解码（旧浏览器、低端设备）** | ⚠️ **1080P 软解掉帧** |
| 浏览器未启用 HEVC 硬解 | ⚠️ 同上 |

**HEVC 软解成本约为 H.264 的 2–3 倍。**

### 已知的相关事实

- 上游另有 `bytevc2`（更私有），已被过滤（无法解码）
- 我们**没有**转码能力（服务端不解码视频）

## 三、其他发现

### 前端缺少 `preload` 属性

**位置**：`RecommendStream.tsx` 的 `<video>`

**现状**：未设置 `preload`，依赖浏览器默认（通常 `metadata` 或 `auto`）。

**影响**：首次缓冲策略不确定，可能延迟起播。

**改进**：显式设置 `preload="auto"` 或 `"metadata"`（按需权衡流量）。

### 切集时重建 video 元素

**位置**：`RecommendStream.tsx:300` 的 `key`

**已派发**：P2 处理。

## 六、经验记录

**「播放卡顿」的第一反应通常是「网络慢」，但实测证明这里是解码问题。**

**测量顺序建议**：

1. 先测吞吐（排除网络）
2. 再查编码格式（解码成本）
3. 最后看前端配置（缓冲策略）

**本次若直接派发「优化网络/代理」任务，会完全走错方向。**
