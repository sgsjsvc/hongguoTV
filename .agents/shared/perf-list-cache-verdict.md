# 列表接口缓存行为测量：与详情接口同一模式

**测量方**: dsh
**日期**: 2026-10-16
**方法**: 冷热对比（`scripts/perf/measure-list-cache.mjs`）

---

## 一、实测数据

### 榜单接口 `/api/rank/list`

| 场景 | 耗时 |
| --- | --- |
| p1 连续 3 次 | 6 → 0 → 0 ms |
| **p4（首次）** | **2079 ms** |
| **p5（首次）** | **1456 ms** |

### 分类接口 `/api/category/list`

| 场景 | 耗时 |
| --- | --- |
| 空标签（已缓存） | 1 ms |
| **`tag=romance`（首次）** | **938 ms** |
| **`tag=period`（首次）** | **888 ms** |
| **`tag=comeback`（首次）** | **854 ms** |
| `tag=romance` 重复 | 1 → 1 ms |

---

## 二、结论：与详情接口完全同一模式

| 接口 | 缓存 | 首次 | 重复 |
| --- | --- | --- | --- |
| 详情 `/api/series/:id` | `pageCache`（180 s） | **1453 ms** | 1 ms |
| 榜单 `/api/rank/list` | 服务端缓存（10 min） | **1456–2079 ms** | 0–1 ms |
| 分类 `/api/category/list` | 服务端缓存（10 min） | **854–938 ms** | 1 ms |

**三个接口都是「缓存有效，但首次访问慢」。**

### 用户实际体验

| 操作 | 体验 |
| --- | --- |
| 重复浏览同一页/同一剧 | ✅ 瞬间（1 ms） |
| **首次浏览新页/新剧** | ⚠️ **等 0.9–2 秒** |
| 超过 TTL 后再看 | ⚠️ 又变慢 |

---

## 三、这印证了「预取」是通用解法

**单纯加缓存解决不了首次访问** —— 这是所有接口的共同特征。

**通用解法**：

| 场景 | 预取时机 |
| --- | --- |
| 推荐流播放中 | 预取下一部剧详情 + 首集清晰度 |
| **用户滚动列表** | **预取视野外 1–2 屏的页** |
| 进入分类页 | 预取默认标签的第 1 页（通常已在缓存） |
| 切换标签前 | 预取相邻标签 |

### 对 P1 的补充

P1（预取机制）应设计为**通用能力**，不只服务详情接口：

```
prefetch(kind, key)   // kind: detail | rank | category | qualities
```

**这样一份基础设施可服务多个场景。**

---

## 四、优先级判断

| 场景 | 用户感知 | 预取收益 |
| --- | --- | --- |
| **切剧**（详情 1453 ms） | 高（每次切都等） | **高** |
| **翻榜单页**（1456–2079 ms） | 中（滚动时才等） | 中 |
| **切分类标签**（854–938 ms） | 中 | 中 |
| 切集（同剧，38 ms） | 低 | 低 |

**结论**：P1 优先服务「切剧」场景，榜单/分类可作为同一基础设施的后续接入点。

## 六、给 P1 的建议

**预取接口设计应支持多种资源类型**，避免只为详情接口定制：

```javascript
// 建议的通用形式
POST /api/prefetch
{ "targets": [
    { "kind": "detail",   "id": "7694..." },
    { "kind": "qualities","id": "7694...", "seriesId": "7693..." },
    { "kind": "rank",     "type": "rank_hot", "page": 4 },
    { "kind": "category", "type": "real-drama", "tag": "romance", "page": 1 }
] }
```

**要求**：并发限制、可取消、失败隔离（已在 P1 brief 中说明）。

**若时间有限**：优先实现 `detail` 与 `qualities`（切剧场景收益最大），
其余类型预留接口但可暂不实现。
